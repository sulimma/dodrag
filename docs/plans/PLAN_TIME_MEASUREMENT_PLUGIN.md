# Time Measurement plugin

Status: implementation plan. The product behavior below was agreed; no implementation is implied.

## Behavior

- Bundle `time-measurement` as a default-off, first-party plugin. Register it with the existing Plugins settings and use separate frontend and Go folders. Assume one person and one running timer; no accounts, attribution, or parallel timers.
- Task Details shows Start/Stop, the running session's elapsed time, the task's saved total, and a session history. Keep a running-task indicator with Stop available when selecting another task or collapsing Details, including any supported window mode that can hide the active task. Do not use the task's Active flag, planned duration, or progress for tracking. Keep elapsed ticks local to the UI; never write to SQLite on every tick.
- Starting the same already-running task is a no-op. Starting another task immediately stops the current timer and starts the new one without confirmation. Use one backend timestamp and one transaction. If the transaction fails, the previous timer keeps running.
- Every stop discards a run under **30 seconds**; exactly 30 seconds counts. Apply this to manual Stop, handoff, completion, normal close, database switch, disabling, and crash recovery. Use one backend helper for the rule. For manual Stop, show brief feedback when a run is discarded.
- Users can edit a saved session's end time or explicitly delete it. Reject an end time that would leave less than 30 seconds or is in the future; do not change the original row on failure. Reject edits that overlap another session rather than double-count time. Make Delete a distinct, confirmed action. These changes are outside global task Undo/Redo.
- On restart after an unclean exit, show the start time of the interrupted run and offer **choose end time** or **discard**. Never count the gap to restart automatically. Resolve the interrupted row before starting a new timer in that database. Keep the prompt actionable even if the task is no longer visible.

## Storage and host integration

- Store sessions in `plugin_time_measurement_sessions` in the task database: stable session ID, task ID plus immutable task-creation event ID, start UTC, nullable end UTC, and elapsed milliseconds for a saved session. Use one consistent precision for time and the cutoff. Enforce one open row with a SQLite unique partial index. Keep no FK to core event rows; Undo/Redo and branch replacement can remove events. A newly created task with a reused visible ID must not inherit an earlier task's time.
- Go owns the schema and typed operations; do not give React a connection, file path to write, or raw SQL bridge. Add the time storage implementation under `internal/plugins/time-measurement/` (Go package name `timemeasurement`) and the plugin UI under `frontend/src/plugins/time-measurement/`. Open/migrate through the eventstore connection; do not introduce a second SQLite writer. Use a per-plugin schema version, migration SQL and version update in one transaction. Keep core event types and payloads unchanged. Follow `AGENTS.md` for the next database-format version and update `MinimumAppVersion` through the normal compatibility path. Because the existing version writer raises the floor on open, document that new builds can upgrade a file even before the plugin is enabled. Test on copies.
- Expose typed state, Start, Stop, end-time update, Delete and recovery calls. Check the saved enabled flag and the expected open-database session under `App.mu`; use a generation for store replacement so stale calls cannot target a reopened copy of the same path. Start also validates that the specified task exists and is not completed. Stop identifies the running session directly. Return the committed timer state, not an optimistic UI update. Use the existing mutation/save coordination, but do not manufacture task events just to refresh a timer.
- Task completion closes the matching timer in the **same SQLite transaction** as the task event, including completion performed through a batch or Redo. Undo never restarts it or changes saved sessions. Add an explicit time-measurement integration at that transaction boundary; do not create a general plugin hook framework yet. Keep a way to stop or recover a timer even if its task is taken out of view by Undo.
- Extend the existing asynchronous close handshake: flush drafts and queued writes, then stop the timer before approving close. Failure leaves the window and timer state available for retry. Stop on a real change of active database before releasing the old store, but not on a cancelled picker or a no-op switch. If stopping fails, keep the old store active. If the timer stops successfully and a later switch step fails, report the switch error without pretending the committed stop was undone.
- For disable, stop the timer under the app lock before saving the disabled setting. Stop failure leaves the plugin enabled. SQLite and the JSON settings file cannot commit together: if stopping succeeds but saving settings fails, keep the plugin enabled, show the confirmed stopped state, and report the settings error. Disabling never removes history.

## Implementation and validation

1. Build the schema and typed Go operations first. Use a controlled clock to test 29,999 ms / 30,000 ms, retrying Start for the same task, handoff rollback, task identity reuse, crash recovery, edit validation and persistence. Verify the format upgrade and that failed migrations don't leave partial schema.
2. Wire completion/Redo, close, database switch, and settings disable. Inject failures to prove completion and handoff roll back together, close stays open, switch keeps the original database, and disable remains enabled on failure. Test stale requests after switching away and back.
3. Add UI for a running timer, saved total and history, editing, deletion and recovery. Keep controls keyboard accessible, announce actions/errors rather than each tick, and follow the 15-language catalog rules. Cover pending/failure states, another task selected, no DB, and disabled plugin.
4. Smoke-test Windows and Kubuntu with disposable databases: switch tasks, complete/undo, close/reopen, switch databases, disable/re-enable, interrupt and recover, and correct a historical entry. Check that timed work never alters planned duration or progress.
